# 10 — DShield Honeypot

## 1. Overview

The CyberSecurity HomeLAB includes a DShield/Cowrie honeypot environment designed to collect and analyze unsolicited internet activity.

The honeypot provides hands-on experience observing real-world reconnaissance, automated scanning, credential attacks, and interactions with intentionally exposed services.

The environment supports cybersecurity learning in several areas:

- Threat monitoring
- Network security
- Honeypot administration
- Security event collection
- Log analysis
- SIEM integration
- Detection engineering
- Incident investigation
- Threat intelligence

The honeypot is deployed as a dedicated Linux virtual machine hosted on Proxmox Virtual Environment.

It operates within an isolated security network and forwards collected telemetry to the Wazuh SIEM.

> **Security Note:** This document is a sanitized representation of the operational honeypot environment. Public IP addresses, exact external port mappings, authentication material, and sensitive firewall configuration details are intentionally excluded.

## 2. Project Objectives

The DShield honeypot was deployed to provide visibility into unsolicited internet activity.

### Primary Objectives

1. Observe real-world reconnaissance and scanning.
2. Collect telemetry associated with unauthorized access attempts.
3. Study automated credential attacks.
4. Analyze suspicious network behavior.
5. Develop experience interpreting security logs.
6. Integrate honeypot events into a SIEM.
7. Create and tune custom detection rules.
8. Practice SOC investigation techniques.

### Security Operations Value

Honeypot telemetry provides an opportunity to investigate activity generated by external systems rather than relying exclusively on simulated security events.

This allows comparison between:

- Expected application behavior
- Automated scanning

- Suspicious connection patterns

Honeypot observations provide investigative leads, but they do not independently establish the identity or intent of the remote actor.

## 4. Honeypot Technologies

The environment uses DShield honeypot infrastructure and Cowrie to collect security telemetry.

### DShield

DShield is associated with the SANS Internet Storm Center and provides a framework for collecting and studying internet attack activity.

The HomeLAB's DShield deployment supports observation of unsolicited network traffic.

### Cowrie

Cowrie is a medium-interaction SSH and Telnet honeypot.

It is designed to emulate interactive services and record attacker behavior.

Depending on configuration and the interactions observed, Cowrie can capture:

- Connection attempts
- Authentication attempts
- Submitted usernames
- Submitted passwords
- Session activity
- Commands entered during emulated sessions
- Session metadata

### Security Value

Cowrie provides insight into how automated tools and other external systems interact with exposed authentication services.

This information can support:

- Credential attack analysis
- Behavioral investigation
- Threat intelligence research
- Detection rule development
- SOC training

The honeypot is intentionally reachable through selected externally published services.

The FortiGate firewall uses Virtual IP objects and firewall policies to direct selected incoming traffic to the honeypot.

### Exposure Design

```text

                      |
                      v
                FORTIGATE
                      |
             SELECTED SERVICES
                      |
                      v
                DSHIELD-01
                      |
                      v
              EVENT COLLECTION
```

Only services explicitly configured for publication are intended to be reachable from outside the network.

### Security Considerations

The honeypot is isolated from trusted internal systems.

Firewall policies restrict unnecessary communication from the security environment to other internal networks.

This is important because the honeypot intentionally attracts untrusted activity.

### Public Documentation Limitations

Exact external ports, destination mappings, firewall policy identifiers, and public IP addresses are intentionally omitted.

## 6. Security Controls

The honeypot environment uses multiple security controls.

### Network Segmentation

The honeypot operates within a dedicated Security VLAN.

This separates it from personal devices, work systems, and infrastructure management services.

### Firewall Enforcement

The FortiGate controls:

- Inbound service exposure
- Inter-VLAN communication
- Outbound internet connectivity
- Administrative access

### Administrative Access

Honeypot administration is performed remotely using SSH.

Management connectivity is controlled through dedicated firewall policies.

### Virtualization

The honeypot runs inside a dedicated virtual machine.

Virtualization provides workload separation and supports backup and recovery operations.

### Monitoring

Honeypot activity is collected through application logs and integrated with Wazuh.

### Defense in Depth

The design combines:

- Network segmentation
- Firewall policies
- Virtual machine isolation
- Controlled service publishing
- Restricted administration
- Centralized event monitoring

No single control should be treated as sufficient protection against every potential compromise scenario.

## 7. Honeypot Logging

Honeypot logs provide the primary source of security telemetry.

### Cowrie Event Collection

Cowrie generates structured events associated with interactions against its emulated services.

Potential event categories include:

- Connection establishment
- Connection termination
- Authentication attempts
- Authentication outcomes
- Interactive session activity
- Command execution attempts
- Session metadata

### Structured Logging

JSON-formatted events support automated parsing and analysis.

A structured event may contain fields describing:

- Event type
- Timestamp
- Source address
- Session identifier
- Authentication activity
- Observed behavior

### Operational Log Monitoring

Linux command-line tools are used to inspect application logs and service behavior.

Examples include:

```bash
sudo journalctl -f
```

```bash
sudo journalctl -u <service-name> -f
```

These commands help troubleshoot service operation and monitor relevant systemd journal entries.

Application-specific log files can also be reviewed when investigating honeypot activity.

### Data Handling

Collected honeypot logs may contain:

- External source addresses
- Submitted credentials
- Command histories
- Session identifiers
- Potentially malicious payload references

Raw event data should be reviewed before being shared publicly.

## 10. Threat Monitoring and Analysis

The honeypot provides visibility into unsolicited activity reaching the exposed services.

### Observed Activity

The environment has generated recurring security events associated with external internet activity.

During monitoring, events were observed arriving frequently, sometimes only seconds apart.

### Investigation Considerations

Relevant questions include:

- What activity occurred?
- When did it occur?
- Which service was targeted?
- What source generated the traffic?
- Was authentication attempted?
- Was an interactive session established?
- What behavior was recorded?
- Does the activity resemble known automated patterns?
- Is further investigation warranted?

### Analyst Mindset

The objective is not simply to count events.

A useful investigation considers the behavior represented by those events.

For example, repeated connection attempts may indicate automated scanning, while recorded interactive activity may provide additional behavioral evidence.

### Threat Intelligence

Honeypot observations can support threat intelligence research.

However, an external IP address or automated connection attempt is not sufficient evidence to attribute activity to a particular threat actor.

## 15. Lessons Learned

Deploying and operating the DShield honeypot provided practical experience with:

- Network exposure management
- Firewall VIP configuration
- Linux administration
- Application troubleshooting
- Honeypot monitoring
- Structured log analysis
- SIEM integration
- Detection rule development
- Alert tuning
- Security event investigation

### Key Technical Lessons

**Internet-exposed services receive continuous unsolicited activity.**

Automated scanning and connection attempts can occur frequently.

**Honeypots require strong isolation.**

Systems intentionally exposed to untrusted activity should be separated from sensitive internal networks.

**Structured logs improve analysis.**

JSON events provide fields that can be searched, filtered, and evaluated by detection rules.

**Detection quality matters more than alert volume.**

High event volume does not automatically indicate high-priority security incidents.

**SIEM integration expands investigative capabilities.**

Centralized event analysis makes it easier to review honeypot activity alongside other security telemetry.

**Operational validation is ongoing.**

Successful initial deployment does not eliminate the need for continued monitoring and testing.
